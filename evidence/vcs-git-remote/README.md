### AC-4.2 (continued) — no write on cancel, confirmation before destructive refs

Every destructive operation is gated by `askConfirm()` (the panel asks; the
backend does not enforce it, and the headless build refuses rather than assumes).
The checks prove "declined → zero writes" for discard, branch delete, tag delete
and remote removal (`vcs.write.discard-confirm-zero-write`,
`vcs.op.branch-delete-declined-zero-write`, `vcs.op.tag-delete-declined-zero-write`,
`vcs.op.remote-remove-declined-zero-write`), and the real-repository E2E repeats
the declined branch/tag/remote cases.

### AC-4.4 — the credential dialog

Runtime: a network operation that fails with git's authentication markers
(`could not read Username …: terminal prompts disabled`, `Authentication failed`,
an SSH publickey refusal, …) triggers exactly ONE credential prompt and one
retry; the request carries the credentials in memory only.

| Claim | Checks |
| --- | --- |
| "no helper / no SSH" really prompts | `vcs.cred.e2e.server` (a real 401 HTTP transport on 127.0.0.1), `.prompted` (1 prompt), `.prompt-content` (the prompt names the remote, not the secret) |
| the credentials really reach the transport | `.transport-received-credentials` — the server saw `Authorization: Basic base64(user:password)` |
| the prompt happens only when authentication is the cause | `vcs.cred.non-auth-failure-no-prompt`, `vcs.cred.classifier` |
| one retry, never a loop | `vcs.cred.prompted-once`, `vcs.cred.retry-only-once` |
| cancel aborts, with git's real reason | `vcs.cred.e2e.cancel-push-requested`, `.cancel-prompted-once`, `.cancel-no-authorization` (no credentials on the wire and exactly ONE git push process), `.cancel-real-reason` (`terminal prompts disabled`), `.cancel-says-aborted` |
| the secret is never rendered in the UI | `vcs.cred.secret-never-rendered`, `vcs.cred.e2e.secret-not-in-ui` |
| the secret never enters argv | `vcs.cred.e2e.secret-not-in-argv` — a `git` wrapper on `PATH` records every argv the backend spawns; the log contains `credential.helper` (the retry configured the helper) and never the secret |
| the secret never reaches disk | `vcs.cred.e2e.secret-not-on-disk` — recursive scan of the whole fixture tree |
| the evidence/logs never contain it | `logs/gate-sensitive-scan.log` — the sentinel is defined once in the lane source and this directory is grepped for it: `matches=0` |

Note on "no helper": git is invoked with `GIT_TERMINAL_PROMPT=0`; the first
attempt configures no credential helper at all, which is exactly the situation a
machine without a helper or SSH key is in. The retry adds an inline helper that
reads the credentials from the child environment — never from argv or a file.

## Boundaries (what this evidence does NOT prove)

* **No real network remote.** fetch/pull/push are proven against real *bare
  repositories on the local filesystem*; the only network-shaped case is the
  401 transport, and it ends in authentication failure by construction. Nothing
  here proves behaviour against GitHub/GitLab (redirects, proxies, tokens).
* **SSH is not exercised.** No `sshd` exists in the pinned image, so the SSH
  publickey refusal path is only covered by the message classifier
  (`vcs.cred.classifier`), not by a real SSH handshake.
* **The modal dialogs ARE now driven** (repair F2/F3): the real
  `CredentialDialog`, `BranchDialog`, `TagDialog` and `RemoteDialog` open their
  real modal `exec()` loop under `offscreen` and are answered by a `QTimer`
  (`ModalDriver`). The default headless behaviour is still "refuse, never invent
  credentials"; only the probe hook forces the modal path.
* **Screenshots exist** (repair F1) — see the six 4a shots above, rendered on
  Xvfb+xcb with per-shot byte/dimension/colour assertions. They render the
  *widgets*, not a full click-through session: the screenshot probe sets the
  widget state directly (selection, dialog fields) instead of synthesising mouse
  events.
* **SVN is untouched.** This batch extends the Git path only; the SVN write
  operations keep their batch-3b behaviour (canned/stub coverage, no real `svn`
  binary in the image).
* **The refs list is capped** at `MAX_REFS = 2000` entries; a repository above the
  cap reports the truncation in `VdVcsInfo.note` instead of silently cutting the
  list. The E2E fixture is far below the cap, so the cap itself is not
  exercised here.
* **`remote -v` (the read) is listing-only.** `git remote add/rm/set-url` are
  *writes* and run through the write gate; the read allow-list rejects them by
  design and that rejection is covered by the Rust test suite
  (`crates/vd-vcs/tests/*`), not by this lane.
