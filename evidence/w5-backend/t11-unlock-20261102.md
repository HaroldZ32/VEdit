## 1. Defect A — the client dropped slang-server on an unknown notification

**Observed (runtime, not code reading).** w5-probe baseline, before any fix
(`w5-probe-20261102T104850Z-baseline.log`):

```
SWITCH-B lastError='backend=slang · cannot open /tmp/w5-probe-…/undeclared.sv on the
  server: initialize failed: service stopped' state=4
SWITCH-B backend=slang ready=1 ready-ms=5 diagnostics-ms=5216
  session='failed: lsp 0/1 file(s), diagnostics 0' diagnostics=0 outline=0
CHECK switch.b.diagnostics-within-5s FAIL
CHECK switch.b.diagnostics FAIL
CHECK switch.b.outline FAIL
```

**Cause.** `crates/vd-lsp/src/client.rs` registered three server→client
notifications (publishDiagnostics / logMessage / showMessage) and left the rest
to `async-lsp 0.2.4`'s default router, which *breaks the main loop* on any
unregistered notification whose method does not start with `$/`:

```rust
// async-lsp-0.2.4/src/router.rs, Router::new default
unhandled_notif: Box::new(|_, notif| {
    if notif.method.starts_with("$/") { ControlFlow::Continue(()) }
    else { ControlFlow::Break(Err(Error::Routing(format!("Unhandled notification: {}", notif.method)))) }
}),
```

slang-server v0.3.1 sends `slang/setConfig` **before** the initialize response,
so the loop died and the pending initialize request resolved as
`service stopped`. `Router::notify` dispatches a registered handler first
(`notif_handlers.get(..).unwrap_or(&unhandled_notif)`), so a catch-all cannot
swallow known messages.

**Fix** (`crates/vd-lsp/src/client.rs`, in `start_session`'s
`MainLoop::new_client` router builder): install
`router.unhandled_notification(..)` that records
`[unhandled notification] <method>` in the client's server-log tail and returns
`ControlFlow::Continue(())`. Unknown *requests* keep async-lsp's default
(METHOD_NOT_FOUND JSON-RPC error), which already satisfies "reply with an error
or ignore".

**Observed after the fix** (`w5-probe-20261102T105545Z-after.log`):

```
SWITCH-B lastError='' lspMessage='backend=slang · buffer changed (169 bytes): …' state=3
SWITCH-B backend=slang ready=1 ready-ms=61 diagnostics-ms=271
  session='degraded: lsp 1/1 file(s), diagnostics 7' diagnostics=7 outline=4
CHECK switch.b.diagnostics-within-5s PASS
CHECK switch.b.diagnostics PASS
CHECK switch.b.outline PASS
SUMMARY checks=38 failures=0
probe-exit=0
```

The three `switch.b.*` the contract names are PASS; the whole probe is 38/38
(baseline: 38 checks / 4 failures — the three above plus defect B).

## 2. Defect B — the batch path dropped verible's syntax errors

**Observed (runtime).** Baseline probe:

```
PROJECT-PASS label=verible-lint engine=verible-verilog-lint engine-id=1 … done=1/1
  tool='verible-verilog-lint' cli-diagnostics=0 message='1/1 文件已扫描 — 0 条 CLI 诊断'
CHECK pass.verible-lint.diagnostics FAIL
```

The real CLI on the very same fixture (probe text, reproduced byte-for-byte in
`t11-cli-vs-batch-20261102T105903Z.log`) exits 1 with **two findings on stdout**
and an empty stderr:

```
/tmp/t11-fixture/undeclared.sv:2:11: syntax error at token "b"
/tmp/t11-fixture/undeclared.sv:4:14-117: syntax error at token "…"
```

**Cause.** `crates/vd-deeplint/src/service.rs::read_verible` parsed
`report.stderr` only. Measured with `verible-verilog-lint v0.0-4298-g085eef05`:
*lint-rule* findings go to stderr (`no-tabs`, `module-filename`, …) but
*syntax errors* go to **stdout** — and a syntax error is all a syntactically
invalid file produces. The probe fixture (`logic a b;`) is exactly that case, so
the batch snapshot was legitimately "0 diagnostics" against a stream it never
read.

**Fix.** `read_verible` parses **both** captured streams
(`parse_verible_output(&report.stdout, …)` then the stderr pass); when the run
still yields nothing and the exit code is nonzero, `MissingOutput` carries the
concatenation of both streams instead of stderr alone. The engine's module doc
now records the split streams. Only the verible branch changed; `read_json`
(slang) is untouched.

**Observed after the fix** (`w5-probe-20261102T105545Z-after.log`):

```
PROJECT-PASS label=verible-lint engine=verible-verilog-lint engine-id=1 … done=1/1
  tool='verible-verilog-lint' cli-diagnostics=2 message='1/1 文件已扫描 — 2 条 CLI 诊断'
CHECK pass.verible-lint.terminal PASS
CHECK pass.verible-lint.diagnostics PASS
```

### CLI vs batch, side by side (`t11-cli-vs-batch-20261102T105903Z.log`)

Same binaries, same files, same process run: CLI is the real
`verible-verilog-lint`, batch is the shipped C ABI (`engine=1`) driven by
`harness/t11_batch_dump.cpp` linked against the rebuilt `libvd_ffi.a`.

| fixture | CLI | batch ABI | equal |
|---|---|---|---|
| `undeclared.sv` (probe text) | exit 1, 2 findings on **stdout** (`2:11`, `4:14-117`, messages `syntax error at token …`) | 2 diagnostics: `line=1 col=10`, `line=3 col=13-116`, same messages, `code=''` | **1** |
| `tabs.sv` (valid file) | exit 1, 2 findings on **stderr** (`module-filename`, `no-tabs`) | 2 diagnostics, same codes/messages, `line=0 col=7-9`, `line=1 col=0` | **1** |

```
COMPARE label=undeclared cli-exit=1 batch-exit=0 cli-findings=2 batch-findings=2 equal=1
COMPARE label=tabs       cli-exit=1 batch-exit=0 cli-findings=2 batch-findings=2 equal=1
```

Position units differ by design: the CLI prints 1-based **byte** columns; the C
ABI carries 0-based line and 0-based UTF-16 columns (`2:11` ↔ `line=1 col=10`),
so ASCII differs by exactly one on each axis. Message text and rule codes match.
