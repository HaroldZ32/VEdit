# r2-c17-probe 结论：KTextEditor 宿主侧 range / semantic-attribute overlay 可行性

**结论：有条件可用（conditionally usable）——且仅限 §0 所声明的探针镜像与版本，不是无条件结论。**

宿主侧确实存在公开的 range 叠加接口，且实测渲染生效、可查询、可随文档移动、可删除回退；
但存在四条硬约束（每行 1024 个属性 range 上限、无文档级属性/range 枚举、无公共语义高亮
API、语义样式必须由应用侧解析主题），因此 R2 只能在该接口之上做“应用侧单一 owner 的
overlay”，不能依赖编辑器替我们仲裁。全部结论均有下面的命令与实测输出支撑。

- Board task: `T7` · 契约: `.mpd/cellwork/cell-20261031T014507403Z/contracts/r2-c17-probe.md`
- 探针源码: `probes/c17-overlay/`（独立 CMake 工程，不改 `src/`、`packaging/`、`requirements`）
- 证据目录: `evidence/r2-c17/`
- 探针镜像: `vprobe-qt6kf6:1`，镜像 id 见 `evidence/r2-c17/00-image-id.txt`；
  Qt 6.10.2、KTextEditor/KSyntaxHighlighting 6.24.0、Ubuntu 26.04 宿主同代发行版。
  **该镜像是自建替代镜像、不是交付镜像；版本依赖、替代原因与 C17 关闭条件见 §0。**

### 2.3 “semantic attribute” 的真实能力边界

- `Attribute::setDefaultStyle(Theme::TextStyle)` **在本探针的环境下（`HOME` 为空、
  使用 KSyntaxHighlighting 内建默认主题 `Repository::defaultTheme(LightTheme)`）
  只可查询、不会被渲染器解析成颜色**：该提示单独使用时文字带饱和色像素 `347 → 347`
  （不变），`INFO defaultstyle_hint_alone_effective=no`。
  **适用范围仅限“默认内建主题”**：本次**没有**在显式命名主题或用户配色方案下做对照，
  因此不能把这个现象写成接口级普遍性质（评审 F4）；若后续要在具名主题下使用
  `setDefaultStyle`，必须先补同型对照实验。
- 应用侧自行从主题解析后再显式设色则可用：`Theme::textColor(TextStyle)` 取到
  `#898887` 后设置 foreground，文字带出现 `87` 个精确同色像素，
  `CHECK semantic.theme_resolved_colors.range PASS`。
- 主题/定义来源：空 `HOME` 下 `INFO embedded_definitions=451 embedded_themes=30
  verilog_loaded=yes` —— KSyntaxHighlighting 6.24 把定义与主题编译进
  `libKF6SyntaxHighlighting.so`（安装头 `KSyntaxHighlighting/repository.h:65`
  “compiled into the shared library”），外部 `verilog.xml` 数量为 0。
  这意味着 `syn-kde-data` 若要走“私有路径加载”必须用 `Repository::addCustomSearchPath()`
  或用户数据目录（本探针不需要外部数据）。

**结论（限定于默认内建主题）：语义着色必须由应用把“语义类 → 主题颜色”预解析成显式
Attribute；公共头文件中没有 semantic highlighting 接口（阴性查证见 §4 / `00-pins.txt`
的 “00b 阴性 API 查证”）。具名主题下 `setDefaultStyle` 是否可被解析未测（F4）。**

## 3. (b) ≥10 万行滚动时的每帧注入耗时

文档：120,001 行（`document_load_ms=55`，`CHECK bigdoc.at.least.100k.lines PASS`），
视口平均 62 行，每次滚动 3 行，共 200 帧；`grab` 为**整窗离屏渲染**（同步、可测），
屏上局部重绘的耗时只会更低，本次未单独测屏上重绘。

| 注入策略 | p50 | p95 | mean | max |
|---|---|---|---|---|
| 全量重建 / 每行 1 个 range（plain 底座） | **16.72 µs** | **27.31 µs** | 17.93 µs | 38.99 µs |
| 全量重建 / 每行 4 个 range（≈248 range/帧） | **66.86 µs** | **107.22 µs** | 73.86 µs | 156.07 µs |
| 增量池（只增删进出视口的行） | **8.42 µs** | **18.70 µs** | 10.53 µs | 26.29 µs |
| 整窗渲染 grab（无 overlay 基线） | 1385.00 µs | 1786.35 µs | 1448.34 µs | 3259.64 µs |
| 整窗渲染 grab（叠加后，全量重建/行） | 1849.58 µs | 2269.24 µs | 1903.77 µs | 2733.92 µs |

Verilog 底座高亮同时开启（120 帧，`02b-run-verilog.log`）：

| 注入策略 | p50 | p95 |
|---|---|---|
| 全量重建 / 每行 | 17.67 µs | 25.67 µs |
| 全量重建 / 每 token | 74.41 µs | 113.74 µs |
| 增量池 | 6.54 µs | 16.51 µs |
| grab 基线（p50） | 1878.81 µs | — |
| grab 叠加后（p50） | 2479.14 µs | — |

**判定：可以增量。**三种策略的注入成本都远低于 16.7 ms 帧预算（最差 p95 113.74 µs，
约 0.7% 帧预算；最差单帧 max 156.07 µs 也仅约 0.9%），增量池最优；真正占帧时间的是
布局/渲染（~1.4–2.5 ms 整窗），而不是属性注入。若采用“每 token 一个 range”，
注意 §5 的 1024/行上限。

## 4. (c) “已存在属性可查询”断言（供 A1g 判据使用）

可以查询（实测全部 PASS）：

```text
CHECK query.range.attribute.identity PASS      # attribute().get() == 施加的 Attribute*
CHECK query.range.start PASS / query.range.end.column PASS
CHECK query.range.zdepth PASS                  # setZDepth(-100) 可读回
CHECK query.range.attribute.name PASS
CHECK query.range.moves.with.document PASS     # 上方插入一行后 range 自动下移，属性保留
CHECK query.range.attribute.survives.edit PASS
```

**不能**查询（阴性查证：命令、空输出与退出码原文见 `00-pins.txt` 的
“00b 阴性 API 查证”一节）：

```text
$ grep -rn 'movingRanges' /usr/include/KF6/KTextEditor/
[exit=1]（无输出）
$ grep -rn 'attributesAt' /usr/include/KF6/KTextEditor/
[exit=1]（无输出）
$ grep -rnE 'movingRanges|attributesAt' /usr/include/KF6/KTextEditor/
[exit=1]（无输出）
```

查证环境：`vprobe-qt6kf6:1`（§0 的 digest）、`/usr/include/KF6/KTextEditor/` 下 25 个
公共头文件、GNU grep 3.12。正对照证明同一查证方式能找到真实存在的 API：
`grep -rn 'virtual MovingRange \*newMovingRange' .../document.h` 命中
`document.h:1489`、`[exit=0]`。
→ 结论：没有 `Document::movingRanges()` 之类的范围枚举，也没有 `attributesAt(cursor)`
之类的逐点属性查询。

**对 A1g 的影响：**“逐 range 单一 owner”必须在**应用侧**用一个 owner 注册表实现：
overlay 只由我们创建（我们持有全部 `MovingRange*`），底座颜色由 KSyntaxHighlighting
独立计算；渲染层已验证 overlay 会覆盖底色（§2.2）。不要设计“向编辑器查询某 range 是谁上的色”，
该 API 不存在。

## 5. (d) 约束、退化方案与对 R2 验收的影响

### 硬约束与限制（逐条标注：实测 / 源码推断 / 未测）

1. **每行属性 range 上限 1024**：同一行 1000 个属性 range → 标记像素 `103568`（正常渲染）；
   1100 个 → 标记像素 `0`（整行属性被静默丢弃）。
   `CHECK cap.ranges.silently.drop.above.limit PASS`。
   → 设计上必须“按行合并 range”或保证单行叠加 range < 1024（例如超长行/压缩文件）。
2. **无文档级查询**（§4，阴性 grep 原文见 `00-pins.txt` §00b）→ 单一 owner 仲裁必须在应用侧。
3. **无公共语义高亮 API**（`grep -rni 'semantic'` 在公共头文件零命中，见 §00b）；
   **在默认内建主题下** `setDefaultStyle` 不参与渲染（§2.3；具名主题未测，F4）
   → 语义色需应用侧解析主题。
4. **渲染开销（p50，整窗离屏渲染）**：plain 基线 1385 µs（`02-run.log:64`
   `MEASURE grab_baseline_no_overlay ... p50_us=1385`）→ 全量重建/行 1849.58 µs
   （`02-run.log:68`，差值 +464.58 µs ≈ +33.5%）、增量池 1810.39 µs
   （`02-run.log:73`，差值 +425.39 µs ≈ +30.7%）；Verilog 模式基线 1878.81 µs
   （`02b-run-verilog.log:10`）→ 2479.14 µs（`:14`，+600.33 µs ≈ +32.0%）、
   增量池 2500.65 µs（`:19`，+621.84 µs ≈ +33.1%）。
   **对账说明**：日志只打印各次 p50（上述行可逐字核对），差值/百分比是用同一日志的
   p50 相减/相除得到的算术值，不是日志里的独立测量；原始 p50/p95 见 §3 两张表。
   旧版本此段曾给出无法在日志中对上的汇总差值，已删除；本段只保留上述可由日志 p50
   逐位核对的数字（评审 F1）。
5. **zDepth 优先级：据上游源码推断，本次未实测。** KTextEditor 6.24.0
   `src/render/katerenderer.cpp:407-417` 显示 zDepth 越小越优先，但探针只验证了
   `setZDepth(-100)` / `zDepth()` 可读回（`CHECK query.range.zdepth PASS`），
   **没有**做两个同区间、不同 zDepth 的 range 的像素级优先级对照；“可用于语义层压过语法层”
   属于待验证的设计推断（评审 F5）。

### 退化方案（若接口在某版本被移除或性能不达标）

- **D1（低风险）**：完全退回 KSyntaxHighlighting 底座着色，不做 tree-sitter overlay；
  单一 owner 由底座独占，A1g 判据退化为“overlay 不启用”，A1h 天然满足。功能上丢失
  tree-sitter 的精确语义着色。
- **D2（中风险）**：自绘 overlay —— 在 `KTextEditor::View` 上叠加透明 QWidget，按
  `firstDisplayedLine()/lastDisplayedLine()/textAreaRect()` 同步 QPainter 绘制。
  需要自己处理滚动/字体度量/光标/选择区，且与编辑器的重绘时序耦合；不推荐作为主路径。
- **D3（高风险、大工作量）**：替换视图/渲染器（同折叠替换，量级 L），只在 D1/D2 都不满足时考虑。

### 对 R2 验收（C16/C17、A1g、A1h）的影响

- **C17 前置成立**：宿主侧确实有 range 叠加接口，R2 的 overlay 落地有明确 API 基础。
- **A1g**：可满足，但策略落点是“应用侧 owner 注册表 + 渲染层覆盖”，不需要也不可能有
  “查询编辑器已有属性”的判据；验收脚本应断言：同一 range 只由 overlay 代码创建一次、
  overlay 打开/关闭两种状态下底色像素的可测差异（本探针的像素断言可直接搬用）。
- **A1h**：可满足 —— 删除全部 overlay range 即回到底座颜色（§2.2 实测），无崩溃；
  底座着色不依赖 overlay 的存在。
- **C16**：单一 owner 的仲裁点由此确定在应用侧；建议 M1 用一个 `OverlayRegistry`
  统一创建/销毁/更新，避免多处持有 range 指针。

  上用同一脚本复跑（§0）。本结论中的所有版本相关数字（1024 上限、451 个内编 definitions、
  p50/p95 等）只属于 §0 的版本组合。
- `setDefaultStyle` 只在默认内建主题（空 HOME）下测过；显式命名主题/用户配色方案未测
  （§2.3，评审 F4）。
- zDepth 优先级只在源码层推断，未做重叠 range 的像素级实测（§5 第 5 条，评审 F5）。
- 未测 KTextEditor 版本升级后的接口稳定性（6.24 → 未来版本）。
