## 2. 正控 / 反向控制（本节是 T64 的核心证据）

夹具：宿主 `/usr/share/org.kde.syntax-highlighting/syntax/` 放 **402** 个明文 XML（400 个 `HostProbeNNN` + `HostLeakProbe` + `SystemVerilog`），用户 `~/.local/share/.../syntax/UserLeakProbe.xml`。

```
== positive (AppDir) ==
CHECK PASS  appdir: defs=2
CHECK PASS  appdir: names == whitelist [SystemVerilog,Verilog]
CHECK PASS  appdir: HostLeakProbe invisible
CHECK PASS  appdir: UserLeakProbe invisible
== reverse control (AppDir) ==
CHECK PASS  appdir-reverse: reverse control reproduces the leak (defs=403)
```

AppImage 上重复同一组（提取后跑，`61-f2-isolation-appimage.log`）：`defs=2`、标记不可见、反向控制 `defs=403`。**正反都过**，说明隔离既成立、测试也真的能抓到破坏。

## 4. 过程中修掉的三个真问题（都不是放宽）

1. **自建库被发行版库覆盖**：装配时先放入 F2 库，随后 `ldd` 闭包从构建镜像里解析同名依赖，把发行版库（2,010,872 B，内嵌 36 个严格 GPL）覆盖回去。修复：放入 F2 库后立刻在 `COPIED[]` 里标记，闭包不再覆盖；断言 `scan-embedded-defs --expect-clean` 必须 PASS。这是 T64 最危险的一个 bug —— 它会静默把交付物打回 GPL。
2. **`LD_LIBRARY_PATH` 污染宿主工具**：AppRun 早期 `export LD_LIBRARY_PATH=$APPDIR/lib`，导致 CentOS 7 的 `/bin/cat` 用宿主 loader 去加载我们的 glibc 2.43，报 `GLIBC_2.35 not found` 并静默输出空串 —— 于是守卫读到空白名单、比较空集合、**假 PASS**。修复：`LD_LIBRARY_PATH` 只在 exec 前导出，所有宿主工具在干净环境下运行；并让守卫在白名单缺失/为空时 `exit 2`（fail-closed），不再静默跳过。
3. **probe 需要 Qt 插件路径**：直接调用 probe 时 `QT_PLUGIN_PATH` 未设置会 `Could not find the Qt platform plugin "offscreen"`。隔离脚本里显式传入 `QT_PLUGIN_PATH`/`QT_QPA_PLATFORM_PLUGIN_PATH`。
