## Assessment

The repair is a real improvement and not a test-only story. The hover popup is now a `QPointer` whose parent is followed by `adoptHoverView()` and whose cache is cleared by the view's `destroyed` connection: the genuine pre-fix product run in `logs/01-red-b3-wiring-e2e.log` dies with no `SUMMARY` right after `destroy.cache-cleared` (the report records exit 139), and the green product run in `logs/09-green-b3-wiring-e2e-offscreen.log` closes the hovered tab, triggers the hover and definition actions, and exits with `SUMMARY checks=48 failures=0`. `ActiveFileWatcher` now subscribes to every open document, `projectRootChanged` re-pins the root and clears the old rows, the panel and session message both use `mergedDiagnostics()`, C8 is implemented as the captain's content rule (saved and unmodified open files included, modified buffers excluded, proven by the two-file E2E), and the modal counter genuinely detects a re-show. I nevertheless fail the lane because the repair introduces a **deterministic stale diagnostic status** and leaves two stale-diagnostic paths:

* the new lower-layer green dot uses `lowerAnalyzed_`, an ever-growing set that is never invalidated when `diagnostics_` is cleared (a file switch starts a new file-scope session, a backend switch re-parses, an explicit reparse resets the rows). A file that the LSP reported with errors turns **green** when the user opens another file, because its lower rows are gone while its path is still in `lowerAnalyzed_`. The clean case is tested (`dot.lower-clean-green`); the invalidation case is not;
* `BackendWiring::applySettings()` clears the lower layer through `controller_->setFileSet({})` but `DiagnosticsController::reparse()` does not clear `coveredFiles_`/`cliDiagnostics_`, and `applySettings()` does not call the new `clearProjectDiagnostics()`. The previous project pass's rows/dots therefore remain under the new backend/lint engine, although the switch comment promises they are cleared (pre-existing, but the repair added the clearing method and did not use it);
* the R2 signal path covers documents only after the 400 ms poll discovers them. A newly opened, already project-pass-covered file edited before its first poll is missed by `ActiveFileWatcher::poll()`'s path-change branch, which sets `lastText_` and returns without `markFileEdited()`; the file then shows the old upper-layer verdict and the merged view suppresses its fresh lower rows until the next observed edit.

The product assertions also overstate their evidence in three places: `hover.probe-off-mouse-path` only checks that the `probePending` key exists (the publisher always inserts it), `destroy.no-stale-pointer` reads a hard-coded `stale=false`, and `destroy.actions-clean` is literally `check(..., true)`; the process-survival crash test is real, but these three checks cannot fail. The screenshots are genuine xcb grabs but the dots shot is a synthetic `QTreeWidget` (no product tree, no icon), `02-window-with-dialog.png` contains no dialog, and the hover shots are widget-only grabs. The product "background tab" check edits B while B is active, so it does not prove background tracking.

## New findings from the repair

### High

**N1. The lower-layer green dot is a stale clean verdict after the analysis that produced it is gone.**
- **Where:** `src/workspace/diagnostics/diagnostics_controller.cpp`, `DiagnosticsController::lowerAnalyzed_`, `DiagnosticsController::analyzeFile()`, `DiagnosticsController::reparse()`, `DiagnosticsController::statusForFile()`, `DiagnosticsController::fileStatuses()`.
- **What:** `collectLspDiagnostics()` inserts every successfully polled file into `lowerAnalyzed_`, including files with error rows. `analyzeFile()` clears `diagnostics_` when it starts a new file-scope session (opening B after A), but does not clear `lowerAnalyzed_`; `reparse()` and a backend switch do the same. `statusForFile()` then finds no lower rows for A and returns `Clean` because `lowerAnalyzed_` still contains A; `fileStatuses()` publishes 3 and the tree paints green. Opening a different file is enough; a file that had errors is then shown as clean. A backend switch (Preferences / settings reload) leaves every previously analyzed file green under the new backend because `applySettings()` calls `setFileSet({})` (which clears only the lower rows) and never `clearProjectDiagnostics()`.
- **Why it matters:** the dot is item 10's only at-a-glance diagnostic state; a green dot means "no errors". A user who opens another file, or changes the backend, is told that a file with errors is clean. This is a stale diagnostic status produced by normal use, not a test-only artefact.
- **Evidence:** `logs/06` only tests `dot.lower-clean-green` (single clean file) and `dot.never-analyzed-unknown`; no test switches files/backends after an errored analysis. The product dot screenshot is the synthetic tree in `b3_wiring_e2e.cpp::shootDots()`, so it cannot catch this.
- **Direction:** clear/refresh `lowerAnalyzed_` whenever `diagnostics_` is cleared (in `analyzeFile()`'s new-session branch, `reparse()`, `applySettings()`), or store a per-file verdict tied to the current session/generation and only report `Clean` when that session completed for the file. Add a regression: analyze an errored file, open another file, assert the first file is not `Clean` and has no green dot.

### Medium

**N2. R2 misses the first edit of a newly opened, already-covered file.**
- **Where:** `src/workspace/diagnostics/diagnostics_integration.cpp`, `ActiveFileWatcher::poll()` (path-change branch) and `ActiveFileWatcher::trackDocument()`; called only from the 400 ms poll.
- **What:** a tab is subscribed only when a poll enumerates it. If the file is opened and edited before that poll, the edit emits no `textChanged` to the watcher. The poll then sees `path != lastPath_`, sets `lastPath_`/`lastText_` to the dirty text, calls `analyze()`, and returns without `markFileEdited()`. If the file was covered by the previous project pass, its upper layer survives; the merged view shows the old upper rows and suppresses the fresh lower analysis. Subsequent polls see unchanged text and do not mark it; only a later observed edit (after subscription) or a new pass clears it, and C8 keeps the file out of the pass while it is modified.
- **Why it matters:** this is the original R2 defect (a stale project verdict superseding the buffer) in a narrower window; opening a project file and typing immediately can show the pass's old verdict until the next keystroke. The product E2E never exercises a newly opened tab edited before a poll; it edits B after several polls and while B is active.
- **Direction:** call `markFileEdited()` on the path-change branch (conservatively, for the newly active file) when the text differs, and/or subscribe on the tab-added/document-created seam rather than only in the poll; add a regression that opens a covered file, edits it before the first poll, and asserts the upper layer is gone.

**N3. A backend/settings switch keeps the previous project pass's rows (pre-existing; the repair added the clearing method but does not use it here).**
- **Where:** `src/workspace/diagnostics/diagnostics_integration.cpp`, `BackendWiring::applySettings()`; `src/workspace/diagnostics/diagnostics_controller.cpp`, `DiagnosticsController::reparse()`.
- **What:** `applySettings()` comments that the old rows are cleared before the new backend answers, but `reparse()` clears only `lints_`, `lspDiagnostics_`, `diagnostics_` and `outline_`; `cliDiagnostics_`/`coveredFiles_` (the project-pass upper layer) survive, and `applySettings()` never calls the new `clearProjectDiagnostics()`. After changing the lint engine/LSP backend in settings, the panel and tree still show the previous engine's project-pass rows under the new engine's status line until a new pass runs.
- **Why it matters:** a stale diagnostic row after a normal Preferences change; the same class as R2. This is not introduced by the repair, but the repair's new `clearProjectDiagnostics()` makes the omission avoidable and the existing comment false.
- **Direction:** call `controller_->clearProjectDiagnostics()` in `applySettings()` before restarting analysis (as `followProjectRoot()` does), or clear the upper layer in `reparse()`; add a product test that runs a pass, switches the lint engine, and asserts no old upper rows remain.

**N4. Three new product checks cannot fail; the report cites them as evidence.**
- **Where:** `src/workspace/diagnostics/selftests/b3_wiring_e2e.cpp`, `hover.probe-off-mouse-path`, `destroy.actions-clean`, `destroy.no-stale-pointer`; `src/workspace/diagnostics/diagnostics_integration.cpp`, `BackendWiring::publishHoverState()` (`state.insert("stale", false)`).
- **What:** `hover.probe-off-mouse-path` only checks that the map contains `probePending` (it is always inserted); `destroy.no-stale-pointer` reads a hard-coded `stale=false`; `destroy.actions-clean` is `check(..., true)`. None can detect the regressions their names imply. The crash itself (process exit 0 after the actions) and the unit `async-returns-immediately` / `async-not-called-inline` checks are genuine, so the substance is covered elsewhere.
- **Why it matters:** the repair report presents these as passing assertions; they inflate the green count and would hide a future regression of exactly the properties they name.
- **Direction:** make the checks assert values (`probePending == true` at the hover instant, a real stale cache field computed from the pointer/state, a real action-state observable), or delete them and rely on the unit/process checks.

### Nit

- **Panel status prints the same merged count twice:** `DiagnosticsPanel::refreshFromController()` appends `mergedDiagnostics().size()` to a session message that already ends in `diagnostics N` (`logs/06`/screenshot `03`: `diagnostics 2 — 2 diagnostic(s)`). One source, but redundant wording.
- **`AUTOFIX-APPLIED … applied=0` is printed before the failure line:** `BackendWiring::applyDiagnosticFix()`; the user-facing message is correct, the log tag is not.
- **C8 empty-pass message:** `DiagnosticsController::startProjectPass()` still says `no files to lint (every file has an open LSP session)` when every file was skipped as a modified buffer; under C8 that is the wrong reason.
- **Double reparse after Open Folder:** `BackendWiring::adoptProjectFiles()` calls `controller_->setFileSet(files)` and `ProjectFileSetPoller::poll()` calls it again; the LSP session is started twice for one root change.
- **Stale hover popup across a project switch:** `BackendWiring::followProjectRoot()` does not hide/clear the hover popup or `hoverEntry_`; if the active view is unchanged, `adoptHoverView()` early-returns on the next poll and the old project's diagnostic bubble can remain visible until the mouse leaves.
- **Split-pane fix target:** `applyDiagnosticFix()` uses `activeView()`/`hoverFilePath_` without checking that the active document is the hovered file; if focus moves to another pane inside the 400 ms adoption window, a fix computed for A can be applied to B's buffer. Narrow, but the guard is one comparison.
- **Server hover cross-view:** `renderHover()` uses `hoverPopup()`/`activeView()` without `adoptHoverView()`, so an LSP hover answer that lands after a tab switch can be placed against the new view into a popup still parented to the old one (invisible). The diagnostic hover path adopts; this one does not.
- **README overclaim:** `src/workspace/diagnostics/README.md` says the project's `.rules.verible_lint` can change the autofix answer, but `BackendWiring::applySettings()` passes only `state_.rulesPath()` (the settings path) and the C ABI does not expose the discovered project rules path (the same limitation is acknowledged in `ffi_backends.cpp`).

## The two required answers

**(a) Can a user still crash or see a stale/duplicated diagnostic by normal use of this tree?**
No reachable crash was found: the popup is a `QPointer`, every use of `hoverPopup_` is null-guarded, the async probe checks a serial and the `destroyed` handler increments it, and the product regression survives the exact action that killed the pre-fix binary. No duplicated rows were found: the merged view is layered and deduped, and the panel/session/status counts now come from one source. **However, a stale diagnostic state is reachable by normal use:** a file that the lower layer reported with errors is shown **green** after the user opens another file (or switches the backend) because `lowerAnalyzed_` outlives the analysis; the previous project-pass rows also survive a backend/settings switch because `applySettings()` never clears the upper layer; and a newly opened, already-covered file edited before its first 400 ms poll keeps its stale upper-layer verdict. So the answer is not a defensible unqualified no.

**(b) Can an automatic save-triggered lint still open a modal dialog?**
No. `BackendWiring::reactToFinishedPass()` passes `ProjectLintNotice::Mode::Automatic` when `DiagnosticsController::lastPassWasAutomatic()` is true, and `ProjectLintNotice::present()` calls `showDialog()` only for `Mode::Explicit`; `dialogsShown` increments on every `showDialog()` and the product run shows `automatic=1 before=2 after=2 visible=0`. The only non-explicit path that could start a pass (`rerunProjectPass()`) belongs to the unmounted `LintProgressBar` and is a user click, not a save.

I would not accept it as the *only* evidence for a Blocker; here the Blocker has the genuine product red.
