## RM-1 模块目录在大工程上整轮失败（**已定位，修中**）

- **现象**：1176 文件的 SystemVerilog 工程，打开后弹出
  `slang failed: lint diagnostics exceeded the 268435456 byte limit`，
  左侧**模块树与接口面板是空的**并显示同一条错误。
- **定性**：`268435456` = `crates/vd-deeplint/src/hierarchy.rs:49 DEFAULT_MAX_JSON_BYTES`
  （`slang --ast-json` 的**字节上限**），服务的是**模块目录**（`catalog.rs:203`；
  C++ `module_tree/catalog_client.cpp:332` 传 0 = 服务端默认）。
  失败文本由 `crates/vd-ffi/src/catalog.rs:306` 拼出，**"lint diagnostics" 是错的措辞**（超的是 AST JSON）。
  结果：整轮目录失败 → 两个已交付需求（item 1/2）在真实规模上直接不可用。
- **量级实测（captain，slang 12.1.0）**：真实形状 1201 文件（top→40 mid→29 leaf，深度 3）
  → AST JSON **22.9 MB**、耗时 **0.12 s**、slang 峰值 RSS **152 MB**。
  玩具模块 5 行就能出 22.9 MB ⇒ 真实模块下 **250–700 MB 是可能的量级**；
  256 MiB 这个上限不算离谱，**错的是"超了就整轮失败"**。
- **修法**：U9a 模块目录必须出树（流式解析 / 或降级为带警告的部分目录，**不许**只改文案、**不许**只调大常量整块塞内存）；
  U9b lint 批量同一类风险（8 MiB 上限 + 去重 + 显式截断）；U9c 把"规模用例"加进门禁（否则下次换阈值还会重演）。
- **状态**：团队 `team-20261106062236044-vp4j-005`，U9a → U9b → U9c + 独立复核。
- **证据**：`evidence/ux-batch-2/u9a-catalog-scale/`、`u9b-lint-flood/`、`u9c-scale-gate/`、`review-u9-final/`。

## RM-2 / RM-3 侦察结论（**这两条已可直接动刀**）

只读侦察把整条链摸清了（`ApplicationShell::projectRootChanged` 一处广播，7 个订阅者）。关键结论：

1. **所有面板状态都是硬替换**（文件树 `beginResetModel/resetRoot/buildRoot`；诊断 `followProjectRoot` 清空并重建 poller；模块目录清 catalog；`ProjectModel::open` 直接 `state_ = ProjectState{}`）——
   **没有"只追加不清"的面板**。所以"堆文件"不是面板 bug。
2. **真正不刷新的是"分析侧的环境"**：`FfiLspSessionBackend` 的 `includeDirs_/defines_` 只有 settings apply 里的 `selectBackend` 会写（`ffi_backends.cpp:437-438`），`followProjectRoot`/`adoptProjectFiles` **从不重推** → 切工程后 LSP 会话仍用上一个工程的 -I/-D。**这就是"环境变量不刷新"。**
3. **祖先配置继续合并**：`vedit.toml` 的 `[project] filelists/include_dirs/defines` 是"从新目录往上找"的（`crates/vd-config/src/project.rs:172-202`）→ 打开大工程的**子目录**时，**大工程的文件清单/定义还在**。**这是"旧文件堆着"最可能的原因。**
4. **分析侧与面板用的是两套输入集**：诊断 poller 与模块目录 fallback 调 `vd_project_expand(..., nullptr, nullptr)`（`diagnostics_integration.cpp:477`、`catalog_client.cpp:284-286`），而面板传了 filelists + settings（`project_service.cpp:87-89`）→ lint/LSP/目录**永远看不到面板显示的那份 `.f` 清单**。
5. `ProjectModel::open()` 无条件 `startExpansion()`（`project_model.cpp:109`）→ 一次切换可能触发多次展开（churn，不是堆积）。
6. 只有一个切换命令 `file.open-folder`（File 菜单 + 工具栏）；文档说"选中的目录只是起点、根会向上发现"，**代码是原样使用**（`app_shell.cpp:403`）。

**变量对话框（RM-3）的确切成因**：`project_variables_dialog.cpp:14-50` 只按"已知/缺失的变量名"生成行，新名字根本无处输入；`project_panel.cpp:329-331` 把对话框的表**追加**进模型 → 已有名字永远删不掉。模型本身能整表替换（`ProjectModel::setVariables`，持久化在 `project-model.json` 的 variables），所以**增/删不需要新 ABI**，是 UI + 契约问题。

**暂不做（已登记）**：让 `defines (-D)` / `include dirs (-I)` 在 Project 面板里也能增删——侦察确认**per-project 存储（vedit.toml）没有写入器**，这两个列表是展开的**输出**；今天唯一的写入口是全局 `settings.toml` 的 `tools.defines`/`tools.include_dirs`。要做需要先决定：写全局，还是新写一个 per-project 写入器（还必须活过 `ProjectModel` 的整状态擦除）。

## RM-5 撤销 / 快捷键（**待定型**）

- **现象（用户原话）**：“撤销不好使，快捷键设置不好使，并且为什么很多功能没有默认快捷键？抄一个吧”
- **三个子问题要分开看**：① 撤销链路（工具栏/菜单 vs Ctrl+Z 可能是两条不同的路）；② 快捷键设置面（是“有界面但不生效”还是“只能看不能改”）；③ 很多命令**没有默认键位**，用户要求照别家编辑器“抄一个”。
- **已定方向**：默认键位按 **VS Code** 抄（Ctrl+Z/Y、Ctrl+S、Ctrl+F/H、F3、Ctrl+G、Ctrl+Shift+F、Ctrl+P、Ctrl+B、Ctrl+W、Ctrl+Tab、F2、F12、Shift+Alt+F…），并保证**不与其他默认冲突**（U3b 已给 registry 加了重复检测，正好用它断言）。
- **待用户回答的两个细节**后定型并派活。
- **可能的坑（已预判）**：A2/U3b 的证据说“撤销/重做真接 KTextEditor edit_undo/edit_redo”，所以“不好使”很可能是**焦点/活动视图**问题（多分屏时撤销作用在非活动视图上）或**快捷键根本没绑到命令上**——两种修法不同。

## RM-5 撤销把视图搞成空白 + 快捷键不生效（**Blocker，修中**）

- **现象（用户原话）**：“一个文件多次点了 Ctrl+Z 以后，它跳出了文件且文件本身直接变成一片大白，什么都没有了，再摁 Ctrl+Z 也没反应了，编辑/撤销都没反应。”
- **严重度定性**：**Blocker（数据安全形状）**。用户随后确认：**磁盘上的内容还在**——关掉标签、选丢弃、再打开，内容完好。
  所以**丢的不是数据，是视图**：视图与文档脱钩、标签变死（既不能编辑也不能撤销），只有"关+丢弃+重开"能救。
  另外用户注意到标签/点的显示在变：修改前是白点，改完是黑点——这条也要一起看（可能与脏标记有关）。
- **已定的两条候选机制**（要让工程师用 file:line 定死，不许猜）：
  1. 应用级 `eventFilter` → `activatePaneContaining` → `setActivePane`（本批分屏激活引入的那条路，按键事件也会进来）；
  2. editor-provider / 标签切换时的 `editor_` 生命周期（本批 A2 就在这里崩过一次——**同一类悬空指针**，很可能那次修得不全）；
  3. `multi_cursor` 在撤销后重放选区；或 `document_sync` 一类"重新加载"路径把文档替换掉。
- **修法要求**：重复撤销**永不**把视图与文档脱钩；若确有必须换文档的场景，必须把视图重新绑到**真文档**而不是空文档；回归要断言"文档指针始终是同一对象 + 文本不会意外为空 + 撤完还能编辑"。
- **快捷键三件事**（同一条用户报告）：① 当前绑定**看不见**；② 改了**不生效**；③ 很多命令**没有默认键位** → 按 **VS Code** 抄一份默认表，并用 U3b 新增的 registry 重复检测断言"没有两个命令共用默认键"。
- **根因（已用数字证明，我原来的“空栈分支清空”假设被推翻）**：**加载文件本身被记成了一步撤销**。打开路径是
  `src/editor/kernel/document_io.cpp:47` 的 `document->setText(QString::fromUtf8(data))`，
  KTextEditor 把 `setText()` 从初始空缓冲**记成一步 undo**。所以**从未改过的文件也有一条撤销记录——就是“加载”**；
  第一次 Ctrl+Z 吃掉它，缓冲合法地变成 `""`。**不存在**任何 `clear()`/`setText({})`/reset 兜底（grep 过：产品代码里没有任何地方清空编辑器缓冲；
  `triggerEditorAction` 在 KTE 动作禁用时只是返回 false，`editor_area.cpp:839-845`）。
  重做在两条派发路径上都是 no-op —— 与用户“重做正常”一致。
  **“文档活下来了”这个推定也不成立**：**内存里的文档确实被清空了**，磁盘文件从未被写过（没保存过），所以“关+丢弃+重开”看到的是磁盘上的内容。
  视图**全程没有脱钩**（同一 QWidget + 同一 document 指针）。
- **修法（已应用）**：改走 `KParts::ReadOnlyPart::openUrl()`（文档化的打开入口），让载入的文本成为**撤销地板**；并在其前置 `setModified(false)`
  （否则 `openUrl()` 内部的 `closeUrl()` 会弹“是否保存”模态——实测会把 kernel selftest 挂住）。实测本地文件 `openUrl` 4–6 ms，offscreen 与 xcb 均正确，
  `modified=false`，撤销停在打开的文本、**永不回到 `""`**。
- **回归**：新增 `src/editor/kernel/undo_view_lifetime_test.cpp`（并在 `src/editor/CMakeLists.txt` 追加了一小段注册——超出声明写域，已主动申报）。
  绿跑 65/65、0 失败，覆盖：零编辑撤销（命令 + 真实按键两条派发路径）、文档身份不变、非空地板、撤销后仍可输入、标签仍显示文件；
  另复跑 `vedit-app-shell-selftest` 与 `vedit-edit-core-selftest ok=1 checks=97 failures=0`。
- **状态**：T10 已交付 → T12 独立复核中；T11（RM-5b 快捷键）已解除阻塞。

## RM-6 Alt 手势被窗口管理器吃掉（**修中**）

- **现象（用户原话）**：“Alt+点击、拖拽好像和窗口的移动重合了”。用户在 **KDE 和 GNOME 都有**这台机器。
- **定性**：`Alt+左键拖拽` 是 KWin/GNOME 的**移动窗口**默认手势，WM 在应用之前就抓走了 → 我们的 `Alt+拖拽`（块选）与 `Alt+点击`（加光标）在 Linux 主流桌面上**根本收不到事件**。VS Code 在 Linux 上把列选改成 `Shift+Alt+拖拽` 就是这个原因。
- **用户裁定（BINDING）**：主手势改为 **`Shift+Alt+拖拽`=块选**、**`Ctrl+Alt+点击`=加/减光标**；`Alt` 版本作为**次要手势**保留（WM 没占用时仍可用）。
- **要求**：`Ctrl+点击`=跳定义**不得**被扰动；普通点击仍是普通点击；一次按下**不能**被两条路径同时处理；矩形插入 + 每列一个光标 + **一次撤销整体回退**这些已验保证保持。手册手势表要改成新主手势并说明原因（一句话：Linux 窗口管理器用 Alt+拖拽移动窗口）。
- **状态**：T13（RM-6，阻塞于 RM-5a 之后，避开 multi_cursor 双写）+ T14 独立复核。
- **附带**：纯键盘的上/下加光标（VS Code `Ctrl+Alt+↑/↓`）本次用户**没选**，留给默认键位批次（RM-5b）酌情加。

## RM-9 红/黄/绿问题点只覆盖"打开过的文件"（**修中**）

- **现象（用户原话）**：“LINT 在文件前面加红点、黄点…现在貌似只在你打开的文件上会显示，其他文件不显示，如果是 FILELIST 导入的貌似根本没地方显示。”
- **用户确认的两点**：① 没打开过的文件**完全没有点**（连灰/空心占位都没有），所以“没点”和“不是文件”看不出区别；② filelist 导入、且在打开目录之外的文件，**只在 Project 面板的 Files 列表里出现**，那里也没有状态列。
- **根因（两条叠加，已定位）**：
  1. **自动工程 pass 的文件集太窄**：只包含“刚保存的文件 + 未修改的打开文件”（上一批裁定的 C8 语义被实现成这个含义），没打开的文件从未被分析 → 没有判决 → 没有点。
  2. **分析侧文件集不含 filelist**：`vd_project_expand(root, nullptr, nullptr)`（`diagnostics_integration.cpp:477`，模块目录 fallback 同）——filelist-only 的文件对 lint 不可见；而文件树是**目录扫描**，目录外文件没有行，就算有判决也无处显示。
- **裁定（已写进任务）**：
  - 覆盖策略：**工程打开 / 显式 Lint Project → 全量**（只跳过脏缓冲区）；**保存 → 只重跑保存的那个文件**，其余判决保留（否则 1176 文件每次保存都全量，不可用）。
  - filelist-only 文件的状态点在 **Project 面板的 Files 列表**里加（那是它唯一的显示面）。
  - **"无判决"要成为可见且可区分的状态**（空心/灰点 + 说明），不能是"什么都没有"；分析后无诊断 = **绿**，不是"无判决"。
  - 不动 R2 分层、一份判决、点由同一份合并视图派生；1176 文件树不得逐文件重绘，pass 必须仍可取消。
- **用户补充修正（关键）**：“刚刚说的点不是'打开过才有'，是'正在打开的文件'才有，甚至是'正在聚焦的文件'才有。”
  → 所以症状比“未打开文件没点”更窄也更深：**只有当前活动/聚焦的文档有点**，切到另一个标签，前一个的点就没了。
  这证明**判决没有被按文件保留**：判决是“为当前显示的文档算一次、然后丢掉”，而不是存成 per-file 状态。
  ⇒ 修法核心：`diagnostics_controller` 必须持有一个 **per-file 判决表**（任何来源层的分析落地都更新它；该文件被编辑时按 R2 规则作废其上位判决），**点由这张表派生**，而不是从“当前显示的诊断”派生；同时不能形成第二套计算——表的输入必须与编辑器显示用的是同一次合并。
- **用户批准**：filelist-only 的文件**可以**也出现在文件树里（例如底部一个“来自 filelist”分组）并带状态点，与 Project 面板 Files 列表那列并存。
- **验收追加（今天全都会红）**：a) 两个文件开两个标签，来回切，**两个点全程都在**；b) 工程 pass 后**工程集里每个文件**都有判决（含从未打开过的）；c) 仅经 `.f` 可达的文件，在树的 filelist 分组**和** Project 面板列表里都有点；d) 脏缓冲区显示明确的“未分析/被排除”态、绝不显绿；e) 1176 文件的树不得逐文件重绘，pass 仍可取消。
- **状态**：T20（Coverage Engineer，阻塞于 RM-2 —— 要等 filelist 管道接通）+ T21 独立复核。

## RM-10 悬浮框只在左侧图标上出现，划线的文字上不出现（**待修**）

## RM-11 把 `.f` filelist 当 HDL 源码解析并报语法错（**修中**）

- **现象（用户原话）**：“不要解析非 RTL 的语法错误，这边在 filelist 文件上还给我报了个错，这玩意儿肯定不行啊。”
- **定性**：`.f` filelist 被当成 HDL 源文件送进了 slang/LSP，于是用户在自己工程的诊断里看到一条“filelist 文件的语法错误”。**filelist 是工程的输入，永远不是源文件。**
- **根因方向**：“这个文件要不要 lint/解析”缺少**唯一判定**——项目扫描、filelist 展开、lint 文件集、模块目录输入、状态点覆盖，各自可能各有一套扩展名判断；缺了过滤就会把 `.f`（以及 `.md`/`.tcl` 之类）送进解析。
- **要求**：
  1. **只有一个源文件扩展名判定**，上述所有消费者都用它（重复的直接合并）。
  2. HDL 集合 = `.sv .svh .v .vh`（若仓库已有更宽的定义，用仓库的并说明位置）；**永不**包含 `.f/.lst/.tcl/.sdc/.xdc/.md/.txt/.json/.toml/.yml`。
  3. `.f` 要被**读取**（`+incdir+`/`+define+`/嵌套 `.f` 按现有 parser），但**不能**作为源出现在 lint 集、目录输入、状态点覆盖里；它出现在 Project 面板的 filelists 列表里是对的。
  4. ~~万一非 HDL 文件漏到了 lint 调用上，必须跳过并记录原因~~ **← 被用户否决（BINDING）**。
     用户原话：“你不应该是加跳过。我的看法是，你应该只解析能解析的文件，这边后续还有多语言支持的想法，如果是加跳过那不炸了吗”。
     改为**正向的能力模型**：一张 **语言/能力注册表**回答“这个路径是什么语言、该语言在本构建里有哪些能力（parse/lint/LSP/format/highlight）”；
     所有消费者（项目扫描含 `vd_project_expand` fallback、filelist 展开、lint 集、模块目录输入、状态点覆盖）都问注册表，不再各自写扩展名判断。
     `.f` **不是语言**、永远不是候选——它是被**读取**的工程清单；注册表里根本没有它的条目，所以不存在“要不要跳过”的问题。
     以后加语言应当是**加数据**（注册一条：语言 + 能力），所有消费者自动跟上。没有可用分析器的情况是一种**状态**（“无可用分析器/尚未支持该语言”），不是跳过日志，更不能变成语法错误。
  5. 回归：一个含 `.f`（指向真实源）的 fixture → `.f` **零诊断**、不在 lint 集与目录输入里，而它列出的源**都在**；另加一个 `.md`/`.tcl` 断言被跳过而非被解析。
- **状态**：已作为 addendum 发给 RM-2（文件集管道的所有者），并另起 **T24** 行做追溯；两者谁先落地由工程师在报告里说明。
